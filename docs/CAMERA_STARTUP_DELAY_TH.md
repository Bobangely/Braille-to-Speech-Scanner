# ลดจอดำระหว่างเริ่มกล้อง

> อัปเดตตามผู้ใช้: ยกเลิก preview native ระหว่าง probe เพราะภาพกระตุกจากการสลับโหมด
> ปัจจุบันคงหน้ารอเดิม พร้อมข้อความ “กำลังเปิดระบบอ่าน / กำลังเตรียมกล้อง กรุณารอสักครู่”
> และแสดงภาพหลังกล้องพร้อมเท่านั้น ผลเวลา preview ด้านล่างเป็นประวัติการทดลองก่อนเปลี่ยนแนวทาง

ตรวจบน Windows x64, OpenCV DirectShow, กล้อง index 0 ที่รองรับ 4K/2K/1080p
ผลนี้เป็น first-open ใน Python process และเปิดซ้ำ ไม่ใช่การตัดไฟกล้องหรือ reboot เครื่อง

## สาเหตุและการแก้

`ThreadedCameraCapture.__init__` เปิดอุปกรณ์และตั้ง MJPG จากนั้น capture thread
ตรวจ 4K → 2K → 1080p → กลับโหมดเป้าหมาย ทุกโหมดตรวจจากสองเฟรมติดกัน
เดิมเฟรมทั้งหมดระหว่าง probe ถูกเก็บภายใน ยังไม่ส่งให้ `read_latest` จึงไม่มี preview
จนตรวจโหมดครบ แม้ driver ส่งภาพได้แล้ว

- ผลก่อนแก้: เปิด DSHOW ประมาณ 0.6–0.7 s, constructor รวมตั้ง MJPG 1.38–1.51 s
- ช่วง probe ทุกโหมด 8.05/9.70 s เป็นคอขวดหลักก่อนเผยแพร่เฟรม
- ไม่พบการเปิดกล้องซ้ำในเส้นทางที่ทำงานสำเร็จ ไม่ได้เปลี่ยน backend, autofocus/exposure หรือค่าความละเอียด
- `camera_reader.py`: อ่าน native frame แรกใน capture thread แล้วส่งให้ preview ทันที และส่งเฟรมระหว่าง probe ด้วยสถานะ `probing`
- ระหว่าง driver เปลี่ยนโหมด ถือภาพล่าสุดไว้แทนจอดำ พร้อมข้อความ warming up
- งดส่งภาพชั่วคราวให้ detection/confirmation จน probe เสร็จ ป้องกันผลจากภาพ native ความละเอียดต่ำหรือภาพระหว่างเปลี่ยนโหมด
- ไม่เปลี่ยนวิธีตรวจโหมดจริง การเลือกโหมดสูงสุด หรือการ fallback; หลัง probe ยังคง 3840×2160 บนกล้องนี้
- การ stop/release ยังคงให้ capture thread เป็นเจ้าของ handle เพียงตัวเดียว ไม่เผยแพร่เฟรมหลังสั่งหยุด

## ผลวัด

| ช่วง | เปิดครั้งแรกใน process | เปิดซ้ำ |
|---|---:|---:|
| ก่อนแก้: เฟรมพร้อมให้ preview | 9.633 s | 11.124 s |
| หลังแก้: เฟรมพร้อมให้ preview | 1.871 s | 1.901 s |
| หลังแก้: ตรวจโหมดครบและพร้อม detection | 11.398 s | 12.361 s |

หลังแก้มี preview native 640×480 ชั่วคราวก่อนกลับ 4K; ไม่ส่ง native preview ไปถอดเบรลล์
การตรวจโหมดทั้งหมดไม่ได้เร็วขึ้น ตัวเลขต่างรอบขึ้นกับ driver/โหลดเครื่อง ไม่ใช้สรุปเปอร์เซ็นต์หรือรับประกันทุกกล้อง

ตรวจซ้ำแบบก่อน/หลังใน process เดียวกันโดยไม่มี suite รันคู่ขนาน:
เฟรมพร้อม preview 11.000 → 1.716 s, ตรวจโหมดครบ 11.000 → 11.502 s,
ความละเอียดสุดท้ายเท่ากันที่ 4K และ capture เท่ากันประมาณ 15 fps
การอ่าน native preview เพิ่มหนึ่งครั้งมีต้นทุน จึงไม่อ้างว่าพร้อม detection เร็วขึ้น

ทดสอบหน้าต่าง scanner จริง: native frame ที่ 1.700 s, render แรก 0.043 s,
ส่ง preview เข้า `cv2.imshow` ที่ 1.765 s; การวัดนี้ไม่รวมเวลาที่จอภาพ scan-out จริง
ระหว่าง session event loop ทำงาน 523 รอบ ช่วงห่างสูงสุด 0.157 s และจบด้วย camera/inference thread หยุดทั้งคู่

ทดสอบ 2K → 4K จริงสองรอบ: ทุกครั้งได้ขนาดเฟรมที่ขอ, capture หลัง warm-up ประมาณ 15 fps,
release สำเร็จประมาณ 0.32 s และไม่มี capture thread ค้าง

## Regression

เพิ่ม `tests/test_camera_startup.py`: preview มาก่อน slow probe, ไม่หายระหว่าง driver call,
การหยุดขณะ first read ไม่เปิด/ปล่อย handle ซ้อน, และ UI แสดงเฟรมโดยไม่ส่ง inference จนพร้อม
ชุด camera ที่เกี่ยวข้อง 36 tests ผ่าน; suite รวม 451 tests ผ่าน รวม resolution fallback,
keyboard controls, camera recovery, detection/parser, UI และ S/B/TTS

ข้อมูลวัดย่อ: [camera-startup-results.json](camera-startup-results.json)

ข้อจำกัด: ยังต้องทดสอบกล้องรุ่นอื่น, MSMF/Linux ARM64 และ cold boot แบบตัดไฟจริง
เวลา autofocus/exposure ภายใน driver ไม่ได้วัดแยกและไม่ได้ปรับเปลี่ยน

## ตรวจหน้ารอที่ใช้อยู่ปัจจุบัน

ยกเลิกการอ่าน/เผยแพร่ native preview และกลับไปตรวจโหมดให้ครบก่อนแสดงภาพ
`scanner_ui.py` แสดงสถานะ STARTING และข้อความกลางพื้นที่ภาพระหว่างรอ โดยใช้ layout/font เดิม
ข้อความหายเมื่อเฟรมพร้อม การรอไม่ได้เพิ่ม sleep หรือบล็อก event loop

ทดสอบหน้าต่างจริง: พบหน้ารอ, ไม่มี probe frame ถูกส่งไป render, ได้ stable preview ที่ 11.704 s
ด้วยความละเอียด 3840×2160 จากนั้นปิดและ release สำเร็จ ไม่มี camera/inference thread ค้าง
Regression ตรวจว่าภาพระหว่างเปลี่ยนโหมดถูกซ่อน ข้อความแสดง/หายถูกจังหวะ และการหยุดกล้องยังปล่อย handle ตามเจ้าของเดิม
