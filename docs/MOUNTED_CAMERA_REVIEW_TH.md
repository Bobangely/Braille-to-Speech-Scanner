# กล้องติดตั้งคงที่: Grid และข้อมูลฝึก YOLO

ตรวจวันที่ 15 กันยายน 2026 บน branch `codex/stable-braille-grid` โดยเทียบกับ working tree ก่อนเริ่มงานรอบนี้ ไม่ใช่เทียบกับ `main`

## สิ่งที่พบจากระบบจริง

ค่าปกติของกล้องคือ `--roi off`: **ไม่ได้โหลดหรือรัน YOLO** แม้ชื่อคลาส/พารามิเตอร์ยังมีคำว่า YOLO อยู่ กล้องใช้ OpenCV ตรวจสี แล้วใช้ geometry จัดจุดเป็นเซลล์ ไม่ได้ใช้ OCR สำหรับตัวพิมพ์ทั่วไป

เมื่อเปิด `--roi yolo` โมเดลปัจจุบันมีคลาสเดียว `0: braille_dot` ใช้กรอบรวมจุดเสนอพื้นที่อ่าน แล้วตรวจสีน้ำเงิน/แดงภายในกรอบนั้น โมเดลยังไม่ได้ตรวจกรอบตัวอักษร/บรรทัดโดยตรง และไม่ได้เป็นตัวตัดสินภาษาไทย

เส้นทางที่ตรวจ: `camera_reader.py` → `YOLOBrailleDetector.detect()` → `ColoredRoiReader` ถ้าเปิดใช้ → `ColoredCellStream.find_dots()` → `plan_cells()` → `CellGridTracker.update()` → `read_cell()` → `pair_markers()` → decoder → worker status → `LivePreview` → ยืนยันข้อความจากผลอ่านใหม่ 6 ครั้ง

| ประเด็น | หลักฐานและข้อสรุป |
|---|---|
| YOLO accuracy | ภาพ diagnostic ที่มีปัญหาชุดล่าสุดใช้ `colored_cell_stream` และไม่ได้รัน YOLO จึงยังกล่าวโทษ weights หรือสรุป precision/recall ของภาพจริงไม่ได้ |
| bbox/ตำแหน่งจุด | เฟรม 4982 มีจุดบนตัว น รวมเป็นก้อน 2,149 พิกเซล ขนาด 86×38 จุดศูนย์กลางจึงไปอยู่กลางสองจุด อีกเฟรมหนึ่งแยกได้ใน mask ดิบ แต่ morphology closing ทำให้เชื่อมกัน |
| ROI/Grid geometry | centroid ของก้อนรวมทำให้สร้างคอลัมน์ผิด; อีกหน้าหนังสือใช้มุมรวมทั้งภาพแล้วแยกแถวผิดตั้งแต่เปิดใหม่ เพราะแนวบรรทัดไม่ตรงกัน |
| Cell ordering | ระบบมี `line_id` / ลำดับเซลล์และ track ID อยู่แล้ว แต่รักษาลำดับของ geometry ที่แบ่งผิดก็ยังอ่านผิด ต้องแก้จุด/แถวก่อน |
| Color filtering | จุดสีรบกวนใกล้ขอบซ้ายของภาพเข้ามาเป็น candidate เพิ่ม แม้ไม่ใช่พื้นที่อ่าน ส่งผลให้จำนวนจุดแกว่งและการยืนยัน layout สะดุด |
| Tracking/temporal | tracker เดิมยืนยันการเปลี่ยน layout 3 ครั้งและใช้จุดปัจจุบันเท่านั้น ตัวแยกก้อนสีเดิมต้องมี Grid ก่อนและเงื่อนไขช่องว่างกลางก้อนเข้มงวดเกินภาพบางเฟรม จึงช่วยตอนเปิดใหม่ไม่ได้ |
| FPS/latency | capture กับ inference แยก thread และเก็บเฟรมล่าสุดอยู่แล้ว ยังไม่พบหลักฐานว่า frame drop เป็นสาเหตุของ geometry ในภาพเหล่านี้ ภาพครอบพื้นที่นอกหนังสือมากทำให้ตรวจสีเต็มภาพเกินจำเป็น |

ภาพหน้าจอ C1–C20 ที่แนบล่าสุดไม่มี diagnostic ดิบที่ตรงกัน จึงไม่อ้างว่าพิสูจน์สาเหตุของ C18 ในภาพนั้นได้แล้ว การแก้และตัวเลขด้านล่างอ้างจากภาพดิบที่มีอยู่ใน `output/diagnostic_*`

## สิ่งที่แก้

1. `colored_braille.py`: เพิ่ม `split_color_components()` ก่อนสร้าง Grid ใช้ distance transform หาแกนสีสองก้อนที่มีหลักฐานใน mask ปัจจุบัน ระยะห่างต้องเข้ากับระยะจุด ขนาดชิ้นต้องเข้ากับจุดใกล้เคียง แยกพิกเซลจริงให้แต่ละก้อน จึงช่วยได้ตั้งแต่เฟรมแรก ไม่เติมจุดจากผลเก่า
2. เลื่อนการกรองสัดส่วน bbox ไปหลังการลองแยกก้อน เพื่อไม่ทิ้งจุดสองจุดที่รวมกันและกว้างกว่าจุดเดี่ยว ก้อนทึบที่ไม่มีสองแกนสีไม่ถูกแยก และยังมีเกณฑ์กรองรูปร่างเดิม บันทึกจำนวนก้อนที่แยกใน `split_color_components`
3. `yolo_cell_stream.py`: แบ่งเฉพาะแถบที่ห่างกันมากกว่า 3 เท่าระยะจุดก่อนประเมินมุม ใช้ระยะจุดร่วมเดิม; หากมุมเดิมจัดครบสามแถวได้อยู่แล้วจะคงไว้ หากไม่ได้จึงลองมุมในแถบนั้นและการ fit สามแถวด้วยข้อมูลตลอดบรรทัด ต้องผ่านเงื่อนไขระยะและ residual เดิมที่สัมพันธ์กับขนาดจุด รักษา source dot IDs และเรียงบรรทัดก่อนซ้ายไปขวา
4. `camera_reader.py`: เพิ่ม `--scan-roi X1 Y1 X2 Y2` สำหรับพื้นที่สแกนคงที่ ค่าเป็นสัดส่วน 0–1 ของภาพกล้อง ตัดก่อน preprocessing/detection และยังใช้พิกเซลต้นฉบับ Zoom/Pan ถูกจำกัดภายในพื้นที่นี้ พิกัด viewfinder/context ใช้กรอบจริงเดียวกัน
5. `tests/test_mounted_reader.py` และ `tests/fixtures/mounted_rows.json`: เพิ่ม 9 tests ครอบคลุมสีน้ำเงิน/แดง จุดเชื่อม ก้อนทึบ มุมต่างกันสองบรรทัด จุดวัดจากภาพหนังสือจริง ROI/zoom/ความละเอียด/ค่าที่ไม่ถูกต้อง และการจำกัดงานเมื่อมี noise จำนวนมาก

ไม่ได้เพิ่ม smoothing หรือเปลี่ยน tracker/threshold การยืนยันข้อความ ไม่แก้ mapping ภาษาไทย ไม่ปิดการตรวจ uncertainty ไม่เปลี่ยน weights ไม่เพิ่ม TTS อัตโนมัติ และไม่เปลี่ยน ownership ของกล้อง/thread

## การใช้งานกับขาตั้งกล้อง

เริ่มด้วยคำสั่งเดิมแล้วดูขอบเขตหนังสือ:

```powershell
.venv\Scripts\python.exe camera_reader.py --lang thai --res 4k --sharp 0 --dot-color blue
```

เลือกกรอบคงที่ให้ครอบทุกบรรทัดที่ต้องอ่านและเผื่อขอบอย่างน้อยหนึ่งเซลล์ จากนั้นเพิ่ม `--scan-roi` เช่น:

```powershell
.venv\Scripts\python.exe camera_reader.py --lang thai --res 4k --sharp 0 --dot-color blue --scan-roi 0.20 0.15 1.00 0.50
```

**ตัวเลขนี้เป็นตัวอย่างที่ใช้ทดสอบกับภาพ diagnostic ชุด 4963–5329 เท่านั้น ต้องปรับตามตำแหน่งหนังสือจริงของผู้ใช้** หมายถึงขอบซ้าย 20%, บน 15%, ขวา 100%, ล่าง 50% ของเฟรมต้นฉบับ ไม่ใช่ค่าที่ hardcode ใน algorithm ค่าเริ่มต้นยังอ่านทั้งภาพ และไม่มีการบันทึก calibration อัตโนมัติ

กด `C` สลับน้ำเงิน/แดงได้เหมือนเดิม หากเปลี่ยนตำแหน่งขาตั้งหรือหนังสือจนพ้นกรอบ ต้องปรับพื้นที่อ่านตามจริง กล้องอยู่กับที่ไม่ได้แปลว่าหน้ากระดาษอยู่กับที่ตลอด จึงยังคง tracking สำหรับการขยับหนังสือเล็กน้อย

สำหรับงานแต้มสีบนขาตั้ง แนะนำเริ่มจาก **fixed ROI + color + geometry + tracker เดิม** ก่อน เปิด `--roi yolo` เมื่อมีข้อมูลพิสูจน์ว่าโมเดลช่วยเสนอพื้นที่ได้ดีกว่า การฝึก YOLO เพิ่มไม่มีผลกับโหมด `--roi off`

## ผลตรวจและข้อจำกัด

- Unit/regression: **138 tests ผ่าน** รวมการเลื่อน/หมุนเล็กน้อย, proposal ผิดสองครั้ง, ลำดับเซลล์, การยืนยันหลายผล, เปลี่ยนสี, scan error/recovery และไม่สร้างกล้องซ้ำ
- เส้นทาง YOLO ด้วย `models/braille_yolo.pt`: **99/99 ผ่าน** เป็น regression ของชุดภาพตัวอย่าง ไม่ใช่ accuracy บนหนังสือจริงที่มี annotation
- CLI `camera_reader.py --help` และ `git diff --check` ผ่าน ไม่มีคำสั่ง lint/build แอปกล้องแยกต่างหากในโปรเจกต์
- Replay ภาพดิบ 52 เฟรมไม่ซ้ำ ตรวจทั้งเปิด reader ใหม่และอ่านต่อเนื่อง ภาพเดิมที่เคยอ่านถูกไม่มีผลข้อความถดถอยในการเทียบชุดนี้ แต่ยังมีภาพเก่าที่ก้อนสีแยกไม่ได้เมื่อเปิดจากเฟรมนั้นทันที จึงไม่อ้างว่าอ่านครบทุกภาพ
- หน้า “นิทานตัว ต / กระต่าย เต่า ต้วมเตี้ยม”: geometry ตอนเปิดใหม่ของเฟรม 3594, 3609, 3618, 3634 จาก 37–43 เซลล์ผิด → **26 เซลล์ / 2 บรรทัด** เฟรม 3610 มีสีรบกวนเพิ่มและยังคงแจ้ง pending เมื่ออ่านต่อเนื่อง
- ภาพล่าสุด 14 เฟรม เมื่อใช้ ROI เดียวกันครอบพื้นที่อ่าน: ข้อความตรง **14/14** ทั้ง FHD และ 4K, คง **33 เซลล์**, ไม่มี warning/pending ในชุด replay นี้ ก่อนแก้ได้ 10/14 ที่ FHD และ 11/14 ที่ 4K การยืนยัน UI ยังต้องสะสม 6 ผลตามเดิม

เวลาอ่าน+decode+วาด preview เฟรมเดียวกันบนเครื่องนี้: warmup 5 ครั้ง แล้ว replay 14 ภาพ 3 รอบ รวม 42 ครั้งต่อเงื่อนไข รันก่อน/หลังแยกกัน ขนาด ROI เดียวกันทั้งสองรุ่น:

| ภาพเข้า | Median ก่อน → หลัง | p95 ก่อน → หลัง |
|---|---:|---:|
| FHD ทั้งภาพ | 53.75 → 50.96 ms | 63.31 → 57.18 ms |
| FHD ภายใน fixed ROI | 37.64 → 38.29 ms | 40.12 → 40.31 ms |
| 4K ทั้งภาพ | 92.85 → 80.70 ms | 103.67 → 92.49 ms |
| 4K ภายใน fixed ROI | 55.16 → 55.58 ms | 62.84 → 61.73 ms |

เมื่อ crop เท่ากัน ภาระ median เพิ่มประมาณ 0.4–0.7 ms; ความเร็วเต็มภาพขึ้นกับจำนวนเซลล์/สถานะที่ต้องประมวลผลและโหลดเครื่องด้วย **ตัวเลขนี้ไม่ใช่ FPS กล้องสด ไม่รวม capture, queue wait หรือเสียง** ไม่ได้เปิดหรือแย่งกล้องที่ผู้ใช้กำลังใช้งาน ต้องเปิดทดสอบจริงหลังแก้และกด D เก็บเฟรมหากยังพบ Grid หลุด

หลักฐานในเครื่อง: `scratch/mounted_review/before.json`, `after.json`, `timing_before.json`, `timing_after.json`, `before_grid.png`, `after_grid.png`, `yolo_regression.json` โฟลเดอร์ scratch และภาพดิบถูก ignore ตามเดิม ไม่ใช่ test fixture ที่ผูกกับ path ในเครื่อง

ควรทดสอบต่อกับแสงสะท้อน/auto exposure, หน้าหนังสือโค้งมาก, จุดแต้มไม่ครบ, สีแดงจริง, จุดเชื่อมจนไม่มีแกนแยก และหน้าที่ต่างจากชุดที่ใช้แก้ สีรบกวนภายใน ROI ยังต้องตรวจหลักฐาน ไม่ละเลยทุกจุดที่อ่านไม่ลง Grid

## เปิดกล้องแล้วให้ YOLO เรียนรู้จากหนังสือได้ไหม

**ใช้กล้องเก็บข้อมูลฝึกได้ ทั้งภาพนิ่งและเฟรมจากวิดีโอ แต่โปรแกรมสแกนปัจจุบันไม่ได้อัปเดต weights ขณะอ่าน** `predict()` และ `train()` เป็นคนละเส้นทาง ข้อมูลที่เหมาะกับงานนี้คือภาพจากกล้อง/ขาตั้ง/ระยะ/ความละเอียดที่ใช้จริง

ลำดับที่แนะนำ:

1. เปิดสแกนหนังสือหลายหน้า กด **P** เก็บ snapshot ไม่มี Grid ทับ หรือบันทึกวิดีโอแล้วคัดเฟรมที่ต่างกัน ส่วน **D** เก็บ `camera_roi.png`, `inference_input.png` และ trace ของเฟรมที่อ่านผิด ใช้ภาพดิบในการทำ dataset ไม่ใช้ screenshot/contact sheet ที่มีกรอบทับ
2. กำกับ bounding box ของจุดจริงและตรวจ label ด้วยคน โมเดลปัจจุบันใช้ **class 0: braille_dot** ไม่ใช่ชื่อพยัญชนะไทยหรือ bbox เซลล์ หากคงหน้าที่โมเดลเดิม ต้องใช้เกณฑ์ annotation เดียวกันกับจุดเบรลล์จริงทั้งหมดที่มองเห็น รวมจุดไม่แต้มสีด้วย แล้วให้ขั้นสีกรองสิ่งที่จะอ่าน การเปลี่ยนไป detect cell/line ต้องเปลี่ยนนิยาม dataset/model และตรวจ API เพิ่ม จึงไม่ได้เปลี่ยนในงานนี้
3. แยก train/validation/test ตาม **หน้าหนังสือและรอบถ่าย** ไม่สุ่มแบ่งเฟรมติดกันของวิดีโอเดียวกันไปทั้ง train และ test คัดเฟรมซ้ำออก เก็บ test ไว้ประเมินเท่านั้น
4. ฝึกเป็นรอบบนคอมพิวเตอร์ ผสมภาพจริงที่ตรวจ label แล้วกับ synthetic ที่หลากหลาย เก็บ candidate weights แยกจาก production แล้ววัด detection, dot/เซลล์/ข้อความทั้ง pipeline และ latency ก่อนเลือกใช้

ภาพจริงที่ควรเพิ่ม:

| ภาพ | เหตุผล |
|---|---|
| น้ำเงิน/แดงจากปากกาที่ใช้จริง แต้มบาง/หนา/ไม่เต็มจุด | ให้โมเดลเห็นความต่างจากจุดสังเคราะห์ที่สมบูรณ์ |
| จุดเล็กตามระยะกล้องจริง ทั้งกลางและขอบภาพ | ตรวจการพลาดจุดเล็กและผลจากการย่อภาพเข้า YOLO |
| จุดติดกัน จุดนูนมีเงา หลายบรรทัด ช่องว่างคำ และ marker เซลล์เดี่ยว | ตรวจการแยกจุดและผล downstream ที่เปลี่ยนความหมายได้ |
| แสงสว่าง/เงา/แสงสะท้อนและหลุดโฟกัสเล็กน้อยตามที่เกิดจริง | ตรวจความทนต่อสภาพกล้องจริง ภาพเบลอจนคนระบุจุดไม่ได้ไม่ควรเดา label |
| กระดาษเปล่า โต๊ะ สันห่วง ขอบหนังสือ รอยปากกาที่ไม่ใช่เบรลล์ | เป็นภาพ/บริเวณลบสำหรับลด false positives; จุดเบรลล์จริงที่ไม่แต้มสีไม่ใช่ negative หากยังใช้ความหมาย class เดิม |

สามารถให้โมเดลเสนอ label เบื้องต้นได้ แต่ต้องตรวจแก้ก่อนฝึก ห้ามนำผลที่โมเดลอ่านผิดกลับมาเป็นเฉลยอัตโนมัติ เพราะจะตอกย้ำข้อผิดพลาด

**ข้อจำกัดเครื่องมือฝึกปัจจุบัน:** `tools/training/train_yolo.py` เรียก `validate_dataset.py` ซึ่งต้องมี `dataset.json`, `records.jsonl` และ metadata จากตัวสร้าง synthetic ภาพจริงที่มีเพียง images/labels/data.yaml ยังใช้ wrapper นี้ตรง ๆ ไม่ได้ ต้องเพิ่มตัวนำเข้า/ตรวจชุดภาพจริง หรือเตรียมชุดตามรูปแบบมาตรฐานสำหรับ Ultralytics แยกต่างหากก่อน งานรอบนี้ยังไม่ได้เพิ่ม importer หรือเริ่มฝึกโมเดล

การแบ่งเป็นเก็บภาพ → ตรวจ label → train → evaluate → เลือก weights ช่วยให้ย้อนตรวจได้ว่ารุ่นใหม่ดีขึ้นจริง เหมาะกับโปรเจกต์จบนี้มากกว่าปรับโมเดลเองทุกเฟรมระหว่างสแกน
