# จังหวะอ่านภาษาไทยด้วย Edge

แก้เฉพาะเส้นทางปุ่ม S → Edge worker; ข้อความบนจอ, Decoder, Thai Assembly และ offline TTS คงเดิม
ช่องว่างหลายช่อง/newline ยังอยู่หลัง `prepare_thai_speech_text`; เดิมส่ง Edge ครั้งเดียวโดยไม่มี pause ที่กำหนดเอง
`edge-tts` 7.3.1 ที่ติดตั้ง escape ข้อความใน `communicate.py` ก่อนสร้าง SSML จึงไม่ส่ง `<break>` เป็นข้อความ

ค่า config อยู่ที่ `edge_stream.THAI_PAUSES_MS`:

| ขอบเขต | Silence ที่แทรก |
|---|---:|
| ช่องว่างหนึ่งช่อง | 30 ms |
| หลายช่องหรือ tab | 80 ms |
| newline / CRLF | 130 ms |
| `. ! ? ฯ` | 200 ms |

หากขอบเขตซ้อนกันใช้ค่ามากที่สุด ไม่รวมบวกกัน; ไม่มี silence นำหน้าหรือท้าย job
จุดระหว่างตัวเลข เช่น 3.14 ไม่ใช่ขอบเขตประโยค ไม่ตัดคำไทยภายในกลุ่มคำ
ชื่อพยัญชนะ 44 ตัวขยายก่อนแบ่งเสียงตามกฎเดิม

ดาวน์โหลด MP3 ตามลำดับใน worker และเริ่มเล่น chunk แรกระหว่างดาวน์โหลด
ใช้ PlaybackDevice เดียวตลอด job ไม่โหลดโมเดลในเครื่องต่อ chunk
แต่ละกลุ่มยังต้องส่งคำขอ Edge ใหม่; คำขอถัดไปเริ่มได้หลังรับ MP3 กลุ่มก่อนครบ โดยมี queue จำกัดสองกลุ่ม
แทรก silence เป็น PCM 24 kHz แล้วรวมใน WAV cache; เปลี่ยน config ทำให้ cache เดิมไม่ถูกใช้
ปุ่ม B หยุด worker/process tree เดิม รวมทั้งช่วง silence; ไม่มี sleep บน UI thread
เสียงอังกฤษและเส้นทาง local Piper/MMS ใช้พฤติกรรมเดิม

ค่าข้างต้นคือ silence ที่แทรกเพิ่ม ไม่รับประกันระยะพักรวม เพราะ Edge มีจังหวะของเสียงเองและอาจต้องรอเครือข่าย
เครื่องหมายจุดที่เป็นคำย่อยังอาจถูกมองเป็นท้ายประโยค ให้ทดสอบเอกสารจริงก่อนปรับค่า

## Speech error กับรายการที่ขึ้นต้นด้วยเครื่องหมาย

พบว่าการแบ่ง `- คำควบกล้ำตัว` เคยส่ง `-` เป็นคำขอเดี่ยว ทดสอบ Edge Niwat จริงแล้วได้ `NoAudioReceived`
จึงรวมกลุ่มเครื่องหมายที่ไม่มีตัวอักษร/ตัวเลขไว้กับคำข้างเคียง เช่น `- คำควบกล้ำตัว` โดยไม่ลบเครื่องหมายหรือแก้ข้อความบนจอ
กรณีนี้เกิดจากการแบ่ง chunk ไม่ได้ยืนยันว่า B เป็นสาเหตุของ error ในภาพ เพราะไม่มี worker log ของครั้งนั้น
ยังคงรายงาน error จากเครือข่าย/บริการตามจริง ไม่ข้าม chunk ที่อ่านไม่สำเร็จเงียบ ๆ

## ผลวัด Windows วันที่ 16 ตุลาคม 2026

ผลวัดต่อไปนี้เป็นของค่าพักชุดแรก 250/425/600/700 ms ก่อนลดเป็นค่าปัจจุบัน:
ข้อความเดียวกัน `เขียด เขียว  ขอน\nไข่.` ใช้ Niwat ความเร็ว -15%:

- ก่อนแก้: first audio 1.09 s, WAV 3.504 s
- หลังแก้: first audio 1.26 s, WAV 8.475 s, 4 chunks, silence เพิ่มรวม 1.275 s
- วัดซ้ำผ่าน controller: first audio 0.88 s; S ระหว่างรอใช้ PID เดิม
- S จาก cache พร้อม marker 0.247 s; B คืนค่าใน 0.0021 s และหยุด worker tree ได้; อ่านหลัง B ใช้ cache ได้

เป็นการวัดครั้งเดียวต่อกรณี ไม่ยืนยันว่า latency ไม่เพิ่มหรือเสียงเป็นธรรมชาติขึ้นสำหรับทุกข้อความ
WAV ที่ยาวขึ้นรวมจังหวะที่ Edge สร้างให้แต่ละ chunk ด้วย ไม่ใช่ silence config เพียงอย่างเดียว
ยังไม่ได้ประเมินการออกเสียงด้วยผู้ฟังหรือทดสอบบน Linux ARM64

ทดสอบด้วย `python -X utf8 -m unittest discover -s tests -q`
ผลรอบสุดท้ายผ่าน 455 tests และ syntax / `git diff --check` ผ่าน
รวม tests ตรวจลำดับ PCM, ระยะ silence ทั้งสี่แบบ, เครื่องเล่นเดียว, cache/config, S/B, 44 ตัว และข้อความต้นฉบับ
