# แก้สถานะ ambiguous_prefix_or_karan

Branch: `feature/fix-c45-recognition`

## สาเหตุจากโค้ด

`thai_decoder.tokenize_thai()` จับ `[356] + [23456]` เป็น ธ และกำหนด
`span=2` สำเร็จแล้ว แต่ถ้าคู่ดังกล่าวอยู่กลางข้อความและไม่มีช่องว่างด้านหน้า
จะเติม warning `ambiguous_prefix_or_karan` โดยไม่ได้มีหลักฐานว่าตรวจจุดผิด
ดังนั้นคำอย่าง วัฒนธรรม อธิบาย และ สิทธิ จึงถูกเตือนทุกเฟรม

เส้นทางที่ทำให้ไม่เห็นข้อความ:

1. `colored_braille.ColoredCellStream.detect()` ตรวจจุดสี วางกริด และอ่าน pattern
2. `yolo_cell_stream.pair_markers()` จับคู่ตามตาราง `THAI_READING_MULTI_CELL`
3. `decoder.decode_cells()` / `decode_cells_verbose()` เรียก Thai decoder
4. `AsyncBrailleWorker._worker_loop()` พบ warning จึงส่งสถานะ `uncertain`
5. `RealTimeBrailleScanner._render_frame()` ล้างประวัติการยืนยันทุกครั้งที่สถานะไม่ใช่ `ok`
6. ข้อความจึงไม่ผ่านเงื่อนไขผลตรงกัน 6 ครั้ง แม้ worker ยังประมวลผลต่อ ไม่มี deadlock

อีกปัญหาคือ `_uncertainty_notice()` ใช้เลขลำดับรายการ แต่กรอบภาพใช้ `track_id`
เมื่อเลข tracking ขาดช่วง ข้อความ C45 จึงอาจไม่ได้หมายถึงกรอบ C45 ที่เห็นบนภาพ

## การแก้และขอบเขต

- ให้คู่ที่ครบ ติดกัน อยู่บรรทัดเดียวกัน และอ่านเซลล์ได้ ผ่านตามลำดับความสำคัญ
  ของ multi-cell ที่ใช้อยู่แล้วใน `pair_markers()` ไม่เติม warning เพียงเพราะอยู่กลางคำ
- `[356] + [23456]` เป็น ธ และ `[356] + [13]` เป็น ฃ
- ถ้าไม่ใช่คู่ที่รองรับ ยังคงอ่าน `[356]` เดี่ยวเป็น ์ ตามตารางเดิม
- ไม่จับคู่ข้ามช่องว่าง บรรทัด ช่องไฟมากเกินเกณฑ์ หรือเซลล์ที่อ่านล้มเหลว
- ข้อความเตือนใช้ `track_id` เดียวกับกรอบ และใช้ลำดับเดิมเมื่อไม่มี tracking
- ไม่เปลี่ยน dot patterns, grid geometry, cell ordering, YOLO, color threshold,
  queue, การยืนยัน 6 ผล หรือการจัดการ error ของกล้อง
- ไม่มี dependency ใหม่ ไม่มีเลข C45 พิกัด หรือคำเฉพาะใน production logic

**ข้อจำกัดที่ยังมี:** กฎนี้เลือกคู่ที่สมบูรณ์ก่อน ไม่ใช่การเพิ่มพจนานุกรมหรือ
การเข้าใจบริบทภาษาไทยทั้งหมด เช่น `จันทร์` ต่อ `ทา` โดยไม่มีขอบเขต มีจุดเหมือน
`จันทรธา` ทุกประการ ระบบจะเลือกคู่ ธ ในกรณีนั้น หากต้องแยกความหมายเช่นนี้
ต้องมีข้อมูลอ้างอิงทางภาษาเพิ่ม การยืนยันหลายเฟรมหรือเทรน YOLO ไม่สามารถ
แยกสองความหมายที่มีจุดเหมือนกันได้

ตาราง [Liblouis th-g0.utb](https://raw.githubusercontent.com/liblouis/liblouis/master/tables/th-g0.utb)
ระบุทั้ง ธ/ฃ แบบสองเซลล์และ ์ แบบเซลล์เดียว ตารางดังกล่าวระบุด้วยว่าไม่รองรับ
การแปลย้อนกลับจากเบรลล์ 6 จุด จึงไม่ควรอ้างว่าตารางให้กฎแก้ความกำกวมทางภาษา
ครบทุกกรณี นโยบายจับคู่ก่อนเป็นการตัดสินใจของโปรเจกต์นี้

## ผลตรวจ

- ก่อนแก้ regression ใหม่ทำซ้ำการเกิด warning ทั้งที่ได้ข้อความถูกแล้ว
  และทำซ้ำกรณี worker ไม่เข้าสถานะ `ok` ได้
- หลังแก้ tests ที่เกี่ยวข้อง 55 tests ผ่าน และทั้งชุด 154 tests ผ่าน
- tests ใหม่ 8 รายการ ครอบคลุม ธ/ฃ ต้นคำและกลางคำ การันต์เดี่ยว คู่ที่ข้าม
  ขอบเขตไม่ได้ เซลล์อ่านไม่สำเร็จ นโยบายเมื่อจุดซ้ำความหมาย ชุดจำลอง 55 เซลล์
  ภาพจุดสีสังเคราะห์ และเลขเตือนที่ตรงกับ track ID
- ทดสอบ worker จริงกับ detector จำลอง: เฟรมแรกกริดกำกวมยังเป็น `uncertain`
  จากนั้นผลที่ถูกต้อง 6 ครั้งจึงแสดง วัฒนธรรม โดย thread เดิมยังทำงาน
  การวาดผลเดิมซ้ำไม่ถูกนับเป็นเฟรมยืนยันเพิ่ม
- เปรียบเทียบก่อน/หลัง 34 กรณี รวมภาพดิบ diagnostic ที่เหลือ:
  ข้อความ dots และ token fields อื่นนอกจาก warning เหมือนเดิมทั้งหมด
- วัดเฉพาะ `decode_thai()` + `tokenize_thai()` สำหรับ 55 เซลล์:
  median ก่อน 0.449 ms หลัง 0.446 ms จาก 6 ชุด ชุดละ 1,000 รอบ
  ต่างกันเล็กน้อยในระดับความแปรปรวน ไม่ใช่หลักฐานว่า FPS กล้องเพิ่มขึ้น
- `git diff --check` ผ่าน

ไฟล์ตรวจซ้ำอยู่ใน `scratch/c45_review/verification.json` (ignored)

## หลักฐานที่ยังขาด

ภาพหน้าจอที่แนบมีข้อความเตือนตามเงื่อนไขที่พบจริงในโค้ด แต่ diagnostic
ที่เหลือใน `output` ณ เวลาทดสอบเป็นภาพ 15 เซลล์คนละหน้า ไม่มี raw image
และ manifest ของภาพ C1–C55 จึงยังยืนยันจุดสีและ token รอบตำแหน่งนั้นทั้งหมด
จากเฟรมต้นฉบับไม่ได้ ชุด 55 เซลล์ใน test เป็นข้อมูลจำลอง ไม่ใช่ replay ภาพนั้น
คำ วัฒนธรรม เป็นการอ่านประกอบจากภาพและใช้เป็นกรณีอ้างอิงทดสอบ
ยังต้องทดสอบหนังสือหน้าเดิมด้วยกล้องจริงและบันทึก D หากพบปัญหาอีก
