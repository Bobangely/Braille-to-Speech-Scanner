# อ่านเบรลล์สีน้ำเงิน/แดงและติดตามกล้องที่ขยับเล็กน้อย

ปรับปรุงบน branch `codex/colored-braille-only` ตรวจล่าสุดวันที่ 13 กันยายน 2026 รอบนี้ไม่ได้ฝึกโมเดลหรือเปลี่ยน dataset และยังไม่ได้ commit/merge/push การแก้เพิ่มเติม

## สาเหตุและบทบาทของ YOLO

โมเดลเดิมมีคลาส `braille_dot` จึงตรวจจุด ไม่ได้จำแนกตัวอักษรไทยหรือหากรอบบรรทัดโดยตรง เส้นทาง YOLO เดิมนำจุดนูนที่ไม่มีสีไปจัดเซลล์ด้วย เมื่อกริดหรือ pattern อ่านไม่ได้ decoder จึงสร้าง `�` (U+FFFD) พร้อมเหตุผล

เส้นทางใช้งานปัจจุบันกรองสี **ก่อนสร้างเซลล์และ decode** จึงไม่นำจุดไม่มีสีมาสร้างข้อความหรืออักขระแทนการอ่านไม่ได้ หากจุดที่แต้มสีเองอ่านกำกวม ระบบยังรายงานความไม่แน่ใจตามจริง ไม่ได้ลบ `?`/`�` ที่ UI

## Pipeline ใหม่

ค่าเริ่มต้น `--roi off`:

```text
Camera → ROI/zoom ของผู้ใช้ → ตรวจสีที่เลือก → กรององค์ประกอบรบกวน
       → จัดบรรทัด/เซลล์ → dot positions 1–6 → รวม marker 2-cell → ข้อความ
```

ตัวเลือกทดลอง `--roi yolo`:

```text
Camera → ROI/zoom ของผู้ใช้ → YOLO เสนอกรอบรวมจุดพร้อมขอบเผื่อ
       → crop ที่ความละเอียดเดิม → ตรวจเฉพาะสีที่เลือก
       → จัดบรรทัด/เซลล์ → dot positions 1–6 → รวม marker → ข้อความ
```

YOLO ทำ overview inference รอบละหนึ่งภาพ ไม่มี tiled/per-cell YOLO inference ในเส้นทาง ROI นี้ กรอบรวมครอบคลุมจุดที่โมเดลเสนอทั้งหมดเพื่อคงบริบทหลายบรรทัดและ marker ก่อนให้ geometry แยกเซลล์ ถ้าไม่พบ ROI จะคืนผลว่างและรอเฟรมใหม่ ไม่ใช้จุดของ YOLO เป็นหลักฐาน decode

ค่าเริ่มต้นไม่โหลด YOLO การเปิด `--roi yolo` เพิ่มต้นทุน inference และอาจพลาดข้อความที่โมเดลหาไม่พบ จึงยังไม่เปิดเป็นค่าเริ่มต้นจนกว่าจะประเมินกับหนังสือจริง หากมีวัตถุสีรบกวนอยู่ภายใน ROI ก็ยังอาจกระทบการจัดกริดได้

## น้ำเงิน/แดงและการอ่านจุด

- รองรับเฉพาะ `blue` และ `red` ค่าเริ่มต้นน้ำเงิน กด `C` สลับระหว่างใช้งาน ไม่รองรับ `green`/`auto` แล้ว
- ใช้ OpenCV แปลง BGR → HSV น้ำเงินใช้ H 100–145 แดงใช้ H 0–15 และ 165–179 ตามสเกล OpenCV พร้อมเกณฑ์ saturation/value
- ปิดช่องว่างเล็กด้วย morphology แล้วกรอง components ตามขนาดและรูปทรง รองรับสีไม่เต็มจุด/ขอบขาดในขอบเขตที่ทดสอบ
- จำกัดจำนวนจุดก่อนเข้า geometry เพื่อไม่ให้ภาพที่มี noise มากทำงานเกินงบ
- จุดสีที่ยอมรับแล้วเท่านั้นเข้าสู่ geometry และ decoder เบรลล์เดิม โดยเรียงแถวก่อนซ้ายไปขวา และคง logic รวม marker เช่น `6 + 13456 → ญ`
- กล้องใช้ sharpening เริ่มต้น `0` เพื่อลดการเปลี่ยนขอบสีจาก preprocessing ผู้ใช้ยังปรับเองได้

ผังจุด:

```text
1 4
2 5
3 6
```

## การขยับกล้องและ lifecycle

ใช้ optical flow บนภาพย่อกว้างไม่เกิน 640 พิกเซลและไม่เกิน 100 จุด feature ตรวจการติดตามไป/กลับ, RANSAC, การหมุน/ขยาย และความสอดคล้องของพิกเซล รองรับการขยับเล็กน้อย ไม่ใช่การกู้ภาพเบลอหนักหรือแก้ perspective มาก

ในโหมด YOLO ROI จะติดตามจากเฟรมที่ YOLO ตรวจล่าสุด เพื่อไม่สะสมความคลาดเคลื่อน และค้นหาใหม่ทุกประมาณ 0.35 วินาทีหรือเมื่อ tracking หลุด ส่วน preview ขยับเฉพาะกรอบ/จุดตามเฟรมผลอ่าน โดยตรึงแถบข้อความไว้ หาก tracking ไม่ผ่านหรือผลเก่ากว่า 1 วินาที จะล้างประวัติยืนยันข้อความและรอผลใหม่

การสลับสีส่ง color/context ไปพร้อมเฟรม งานที่เริ่มก่อนสลับสีจะถูกทิ้งเมื่อเสร็จ จึงไม่เอาผลสีน้ำเงินมาแสดงหลังเลือกแดง ไม่โหลดโมเดลซ้ำ และยังใช้ worker กับ camera session เดิม การอ่านเฟรมไม่ได้หรือ inference exception ใช้เส้นทาง recovery เดิม ไม่ restart กล้องทุก error

แก้เพิ่มเติมจากรีวิว: พิกัด bounding box หลัง crop ต้องเป็นจำนวนเต็มสำหรับ OpenCV, คืนพิกัด reading axis ให้ตรงภาพต้นฉบับ, ล้าง ROI ก่อน inference ที่อาจล้มเหลว, เว้นระยะกรณีหา ROI ไม่พบ และทำให้ภาพสถานะรอวาดได้แม้ผลก่อนหน้ามีแถบข้อความหลายบรรทัด

## คำสั่งใช้งาน

```powershell
.venv\Scripts\python.exe camera_reader.py --lang thai --res fhd --dot-color blue
```

กด `C` สลับน้ำเงิน/แดง, `D` ส่งออก diagnostics, `P` บันทึก snapshot, `Q`/Esc ออก เพิ่ม `--roi yolo` เพื่อทดลอง ROI จากโมเดล เลือกเริ่มด้วยแดงโดยใช้ `--dot-color red`

ภาพเดี่ยว:

```powershell
.venv\Scripts\python.exe yolo_detector.py path/to/raw_image.png --lang thai --dot-color red --roi yolo --save --dump-stream --no-show
```

Diagnostics มี input ที่อ่านจริง, crop รายเซลล์, Unicode ของข้อความ, เหตุผลความไม่แน่ใจ, สีของเฟรมนั้น, `roi_mode`, `roi_source` และ `yolo_inference` จึงแยกเฟรมที่ใช้ YOLO กับเฟรมที่ติดตามกรอบได้ โดยสีเป็นแหล่งข้อมูลอ่านจุดเสมอในสองโหมดนี้

## ผลตรวจและสิ่งที่ยังต้องทดสอบ

รีวิวก่อน merge วันที่ 14 กันยายน 2026 พบว่าคำสั้น `กา` ที่ย่อเหลือ 25% มี feature เพียง 6 จุด แม้ถอดรหัสถูกต้อง แต่การเลื่อน 1 พิกเซลทำให้ tracking เดิมที่ต้องการ 8 จุดปฏิเสธผลและล้างความนิ่ง แก้โดยเพิ่มเส้นทางสำหรับ 3–7 features ซึ่งยอมรับเฉพาะ translation ไม่เกิน 8 พิกเซลบนภาพ tracking ทุก feature ต้องผ่านการตรวจไป/กลับและมี displacement สอดคล้องกัน จุดต้องกระจายสองมิติ และตรวจความสอดคล้องของพิกเซลด้วยเกณฑ์ที่เข้มขึ้น ไม่ลดเกณฑ์ของเส้นทาง RANSAC เดิม

หลังแก้ผ่าน **103 unit/regression tests** รวมกรณีคำสั้นเลื่อน 1–2 พิกเซลแล้วเข้าสถานะ LOCKED และกรณีต้องปฏิเสธ: จุดหาย/เพิ่ม, เปลี่ยนฉาก, เบลอหนัก, เลื่อนมาก, feature น้อยกว่า 3 หรือเรียงแถวเดียว เส้นทางนี้ไม่ได้รับรองการหมุน/เปลี่ยนขนาดเมื่อมี feature น้อย หากยืนยันไม่ได้ยังรอผลใหม่ตามเดิม

Build source distribution และ wheel ผ่าน แต่ wheel ปัจจุบันยังบรรจุเฉพาะ placeholder package ซึ่งเป็นข้อจำกัดเดิมก่อน branch นี้ การใช้งาน scanner ที่ตรวจคือ source CLI ตาม README; ยังไม่ใช่การยืนยันการติดตั้ง scanner จาก wheel และยังไม่ได้ทดสอบกล้องจริง/บอร์ดในรอบนี้ ผล benchmark ด้านล่างเป็นข้อมูลจากรอบตรวจที่ระบุ ไม่ใช่ FPS ของกล้องจริง

- Full suite ผ่าน **99 tests** รวม regression ใหม่ที่ยืนยันว่าแถบสถานะรอวาดไม่ได้ก่อนแก้ และวาดได้หลังแก้
- ครอบคลุมการเลื่อน/หมุน ±3°, ภาพเปลี่ยนฉาก/เบลอหนัก, ขอบสีขาด, สลับสีระหว่าง inference, ผลล่าช้า, ROI exception และการคืนพิกัดให้ renderer
- ทดลอง `models/braille_yolo.pt` จริงบนภาพสังเคราะห์สองสี ทั้งตรงและเอียง 3° ผ่าน **4/4 กรณี**: เลือกน้ำเงินได้ `กญา`, เลือกแดงได้ `กภา` แยกสีถูกต้องในตัวอย่างนี้
- Benchmark เส้นทาง YOLO เดิมผ่าน **99/99** เป็นคนละชุดกับ 99 unit/regression tests
- ผลในเครื่องอยู่ที่ `scratch/handheld_20260913/roi_smoke.json`, `red_roi/annotated.png` และ `yolo_regression.json` ซึ่งถูก gitignore

ยังต้องทดสอบกล้องถือมือกับหนังสือจริง ทั้งแสงสะท้อน หมึกจาง ระยะถ่าย สีรบกวน หลายบรรทัด และเปรียบเทียบ `--roi off`/`--roi yolo` รวมถึงวัด latency/FPS และการใช้ทรัพยากรบน Redxa ผลสังเคราะห์ข้างต้นไม่ใช่ความแม่นยำของหนังสือจริง และยังไม่ยืนยัน FPS กล้องหรือบอร์ด เครื่องที่ inference ช้ากว่าเกณฑ์อายุผลอาจแสดงสถานะรอบ่อย ต้องวัดก่อนปรับเกณฑ์
